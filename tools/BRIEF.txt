A phone-first 3D web page with five playable core-loop demos on one shared kit (three.js r128 global THREE; cannon.js 0.6.2 global CANNON is also loaded).
The owner will play each demo for about a minute on a phone to decide which idea to build out. Each demo is ONE polished slice of a core loop:

READ FIRST (all short, commented): ROOT/kit/core.js, input.js, fx.js, sfx.js, make.js, ui.js, post.js, physics.js, shell.js, and ROOT/tools/example-game.js (uses every API).

The contract: your file calls Kit.register({ id, name, tagline, hook, color, order, create(ctx) }) and create returns { update(dt, t), dispose?() }.
ctx gives: THREE, scene, camera, size{w,h,aspect,portrait}, math, fmt, input, fx, sfx, ui, save, make, pool, after/every/tween (game-time), on('resize'), restart(), exit(), paused, timeScale.

Rules of the kit:
- Colours: the renderer outputs sRGB. Always build materials through ctx.make.* (make.mat, make.box, ...) or convert with make.color(hex). A raw new THREE.Color(hex) will look washed out.
- input.stick.y is screen-space (positive = down the screen = toward the camera in a top-down view).
- The shell disposes the scene, HUD, input and timers on exit/restart. Use ctx.after/every/tween, never setTimeout/setInterval/requestAnimationFrame. Do not add window/document listeners.
- HUD only through ctx.ui (stat, progress, actions, choose, banner, toast, hint, el). No emoji anywhere. Keep at most 3 stats so the top row fits a 390px phone.
- Top ~110px and bottom ~90px of the screen are HUD; keep the action in between. Design for portrait 390x780 first; it must still work in landscape.
- Performance: phones. Pool anything spawned repeatedly (ctx.pool), share geometries/materials, use THREE.InstancedMesh for crowds, keep live meshes under ~200, one shadow-casting sun (make.stage).
- Feel: every player action gets feedback within one frame: sound (ctx.sfx.play), particles (fx.burst), and where it fits shake/hitstop/ring/floater/tween squash. Camera should move smoothly (math.damp).
- A player who taps nothing for 3 seconds should still understand what to do (ui.hint, hide it after first input).
- End states use ui.banner(...).then(() => ctx.restart()). Save a best score with ctx.save.

Code style: one file, plain ES2019 classic script wrapped in an IIFE or just the Kit.register call. Tunable DATA TABLES at the top
(upgrades, enemy types, levels, costs as plain objects/arrays) and small pure functions that read them, so adding content later means adding a row.
Aim for roughly 250-450 lines. Clear names, short comments only where the why is not obvious.

Writable paths (nothing else): ROOT/games/<your id>.js and ROOT/scratch/<your id>/ for any scratch files. The smoke tool writes ROOT/shots/<id>-mid.png and -end.png.
The kit files and index.html are read-only for you. If the kit lacks something or has a bug, work around it inside your file and report it in "Kit gaps" (a later pass folds good ideas into the kit).

CODE STANDARD (the owner's review of the code so far: sloppy. This section is binding for every file you write or touch.)
  Names     - Say what a thing is. No single letters or abbreviations outside tiny lambdas and loop indices: `enemy`, `spawnInterval`, `options`,
              not `e`, `si`, `o`. Functions are verb phrases (`rollAffixes`), booleans read as questions (`isMaxed`, `canAfford`), constants are UPPER_SNAKE.
  Docs      - Every exported or shared function, factory and data table has a JSDoc block: one sentence on what it is for, @param / @returns with
              types and units, and an @example when the call shape is not obvious. Row shapes get a @typedef. Each file opens with what it owns and what it does not.
  Comments  - Explain the logic and the why at each non-obvious step (the invariant, the edge case, the reason for a constant), so a reader can follow
              what is happening without running it. Never restate the code; never leave a clever line unexplained.
  Structure - Small functions that do one thing, composed. Prefer pure functions over closures that mutate shared state; keep simulation (plain data
              in, plain data out) apart from rendering and input. If two places do the same thing, extract it; if a helper is generic, it goes in the kit.
  Higher-order - Use map / filter / reduce / flatMap and functions that take or return functions (pipelines, combinators, curried builders, strategy
              tables keyed by id) instead of index loops, flag variables and switch ladders, except in measured hot paths (say so in a comment).
  Data      - Tunables live in named tables and curves at the top, never as literals buried in logic. One source of truth per fact.
  Hygiene   - No dead code, no commented-out code, no unused variables, no magic numbers, no copy-paste blocks, consistent formatting, early returns
              over nesting, errors that name the cause. Leave any file you touch cleaner than you found it.
  Tests     - Pure logic is covered in tools/test-kit.js with cases that would fail if the logic were wrong (edges, not just the happy path).
Review your own diff against this list before you report, and say in the report what you cleaned up.

THEME (the owner's review: every game's UI looks the same; implementers had no way to make native-looking UI). The kit now has a customisation layer:
read ROOT/kit/theme.js (short, documented). Every game MUST give itself a HUD that belongs to its own world by adding `theme` to its Kit.register call:
  theme: {
    skin: 'glass' | 'neon' | 'pixel' | 'paper' | 'stone' | 'toy' | 'air' | 'parchment',   // a starting point, not the answer
    fonts: ['Family Name:wght@500;700'],            // Google Fonts only
    tokens: { '--accent': '#...', '--panel': '...', '--radius': '...', '--display': '...' },  // any token in Kit.theme.TOKEN_DEFAULTS, or your own
    layout: { stats: 'top-right' | 'top-center' | 'top-left', actions: 'bottom' | 'bottom-right' },
    css: '& .stat { ... }',                         // extra CSS scoped to your game ("&" = your game's HUD root)
    components: { stat: ({ label, value, h }) => el, action: ({ id, label, sub, h }) => buttonEl },  // rebuild a component; keep the live elements you are given
  }
Do not stop at picking a skin: two games on the same skin must still look different. Choose type, colour, shape and placement from your game's fiction

DEPTH (the owner's review: every game so far lacks any depth in gameplay or progression). See AGENTS.md principle 5; this replaces every earlier
"one-minute slice" framing. Every game must have depth at three timescales and state it in its file header:
  seconds - mastery: the basic action can be done well or badly and skill shows.
  minutes - decisions with trade-offs and systems that interact (synergies, counters, risk against reward) so runs and builds differ.
  hours   - a long arc that changes how you play: unlockable mechanics, tools, modes, places or characters, goals that pull you back, difficulty that
            grows with the player's power. Bigger numbers alone do not count.

Kit.synergy (kit/meta.js: tag-based set bonuses feeding Kit.stats), Kit.upgrades with requires (trees), Kit.loot / Kit.inventory, Kit.goals, Kit.curve,
Kit.spawnTable. Design the depth first as a short plan in the file header (the three scales, the interacting rules, what unlocks when), then build it,
preferring a rule that interacts with existing rules over a row that does not. Prove the pacing: keep the game's economy and progression as pure
functions and simulate hours of play headlessly with simple bot policies (a script in your scratch folder, or contribute a shared simulator to tools/),
then report the curve (time to each unlock, when the player runs out of new things). The first minute must stay as inviting as it is now.

DEV TOOLS HOW-TO (tools/dev.js; every command is also a make target, `make help`). Use these instead of one-off scripts.
  node tools/dev.js new game <id> [--skin neon]     a working game that already meets the standard: header with the depth plan, tables, theme,
                                                    Kit.fsm phases, Kit.upgrades + Kit.profile, a headless model, debugState(), its script tag,
                                                    scratch/<id>/play.json and scratch/<id>/PLAN.md (the lead's plan). Undo: remove game <id>.
  node tools/dev.js new module <name>               a pure kit file with header, one documented function, its test stub and its script tag.
  node tools/dev.js check [id...] [--fast]          ONE table: unit tests, script tags, lint, Biome, type ratchet, smoke, frame budgets. Exit 1 on FAIL.
                                                    With ids, only your files can fail it; problems in other files show as WARN. --fast = no browser.
  node tools/dev.js play <id> --script <file>       scripted playtest. Steps (text or JSON objects): tap <point> [xN], drag <p> <p> [in s], swipe <dir>,
                                                    hold <p> <s>, key <name>, press <HUD label>, choose <index|label>, wait <game s>,
                                                    until <predicate> [timeout s], assert <predicate>, log <expr>, timescale <n>, shot <name>, restart.
                                                    Points: center left right top bottom, or x,y (0..1 = fraction, else pixels). Predicates are JS over
                                                    `state` (your debugState()), `hud` (label -> value), `time`, `modal`. Shots go to scratch/<id>/.
                                                    Inline: play miner "tap center x5" "wait 2" "assert hud.Depth >= 1". Flags: --landscape --skin --touch.
  node tools/dev.js sheet | skins <id>              contact sheet of every game, or one game under every skin, into shots/.
  node tools/dev.js lint [paths] [--summary]        file:line, rule, one-line fix. `lint rules` lists the rules. Hard rules (header, TODO, console.log,
                                                    raw timers / listeners in games) fail check; the rest are heuristics and warn.
  node tools/dev.js docs                            regenerates kit/API.md from the JSDoc (signature, params, returns, @complexity, examples).
  node tools/sim.js <id> [--hours 2]                plays headless.progression with greedy / random / saver bots; see AGENTS.md "Headless model".
  node tools/dev.js types [file] | tags [--fix] | format <your files> | bench | metrics | snapshot <file> + replace <file> --with <copy>
In your game: return debugState() from create() next to update(); it feeds play predicates and the developer overlay (backquote key in the page).
